*Основа: официальные PDF Freedom Broker и уточнения организаторов, присланные в Telegram 8 ноября 2026.*

## Перед стоп-кодом

- [ ] В интерфейсе работают «Диалоги», редактирование чек-листа, оценка с 8 критериями, переход к реплике, апелляция и решение проверяющего.
- [ ] Проведён хотя бы один реальный вызов ИИ из интерфейса (`MOCK=0`); прежние импортированные результаты сами по себе не доказывают доступность нового вызова.
- [ ] `python3 -m unittest discover -s tests -v` — тесты проходят.
- [ ] Исходный `DEV` — 65 записей. В `results/dev/results.json` ровно 65 уникальных `conversation_id`, 8 критериев на успешную оценку.
- [ ] Когда организаторы выдадут **10 PROD-чатов**, выберите `PROD` в «Диалоги», импортируйте JSON (или HTTPS GET), оцените все 10. Проверьте `results/prod/results.json` — ровно 10 записей, без повторяющихся ID. Если была ошибка, сохраните её по схеме `status=error` — не подставляйте фиктивный балл.
- [ ] `results/dev/results.json` и `results/prod/results.json` отправлены в Git (`commit` **и** `push`) до стоп-кода.
- [ ] Git-репозиторий **открыт для просмотра к стоп-коду**. Проверьте доступ по ссылке в режиме без авторизации.
- [ ] В Git лежит **весь исходный код**, включая `web/index.html`, `web/styles.css`, `web/app.js`, `server/`, `start.py`, `requirements.txt`, `README.md`.
- [ ] `.env`, токены, SQLite, кэши и аудиозаписи с личными данными **не попали** ни в актуальный коммит, ни в историю Git. Проверить `git status`, `git ls-files` и историю.
- [ ] После стоп-кода **не менять исходный код**. Презентацию по уточнению организаторов корректировать можно.

## Особый случай contact в DEV-звонках

В приложении к заданию официальный тип `contact` — `true/false`. Организаторы в Telegram допустили самостоятельную методику для неполных DEV-звонков, но **не подтвердили явно**, что `null` допустим в официальном JSON 1.0. Для наименьшего риска схема официального экспорта оставлена бинарной. При неполном начале звонка ИИ обязан писать, что **проверка приветствия ограничена доступным фрагментом**, а не утверждать бездоказательно, что оператор не здоровался. По возможности используйте аудиозапись, затем ручной пересмотр. В контрольном PROD **звонков нет**.

## Сценарий живой демонстрации (около 5 минут)

1. **Обзор и данные** (40 сек). Показать RU/KZ/EN, DEV и PROD, импорт JSON или по ссылке.
2. **Редактор чек-листа** (50 сек). Скопировать или изменить критерий, сохранить новую версию. Не менять готовую официальную версию задним числом.
3. **Анализ диалога** (90 сек). Показать 8 оценок, N/A там, где допустим, итог и переход к точным репликам.
4. **Апелляция** (60 сек). Оспорить критерий; как проверяющий показать цитаты, изменить или подтвердить значение, получить новый итог.
5. **Выгрузка** (40 сек). Показать DEV 65/65 и PROD 10/10 после обработки; объяснить JSON 1.0 и открытый Git.

**Важнее всего продукт.** Слайды опциональны; достаточно 1–2 вспомогательных. По уточнению в Telegram всё выступление вместе с вопросами жюри ограничено 8–10 минутами. Хостинг не обязателен и не заменяет Git с исходниками.

## Что не следует обещать

- Стабильный повторный балл обеспечивается **сохранением результата**, а не гарантированной эталонной точностью ИИ.
- Система **не делает автоматический push в GitHub**; «Результаты и выгрузка» готовит файлы для ручного коммита.
- Приложение может показать аудиоссылку DEV-звонка, но **не анализирует интонацию непосредственно из звука** и не заявляет, что прослушало запись.
- Успешные тесты приложения без Gemini-ключа не равны проверке реального доступа к API и квот.

## Дополнительная демонстрация: аудит сохранённых оценок

Раздел «Аудит оценок» — добровольная функция сверх обязательного чек-листа хакатона. Покажите сортировку «от худшего к лучшему», выберите один спорный диалог, откройте проверку и сравните обоснование ИИ с пронумерованными репликами. Аудит не делает новых вызовов Gemini и не заменяет апелляцию с человеческим решением. Сохранённые баллы и экспорт JSON остаются прежними.
